# Change log

Every change to [plan.md](plan.md) and [outline.md](outline.md), oldest first. The plan marks each changed decision with the chapter that changed it, and this file says why.

| Chapter | Change | Why |
|---|---|---|
| ch00 | Plan written from the design session on 2026-10-08 | Starting point. |
| ch01 | Added dialect details: `= {}` and designated initializers, C-style casts, how `ASSERT` stops, `i32` counts and `i64` sizes, `UPPER_SNAKE` constants, `-Wno-missing-field-initializers` | Writing `base.h` and its test program needed them, and the plan didn't cover them yet. |
| ch02 | Moved loading `game.so` with `dlopen` and the `GameApi` struct from chapter 06 to chapter 02 | A `game.so` that nothing loads would prove nothing. Chapter 06 keeps the reloading itself. |
| ch02 | Added the boundary and build details: `momo.h`, `-fvisibility=hidden`, `extern "C"`, `RTLD_NOW`, `$ORIGIN`, `--no-undefined`, the build folder layout, `compile_commands.json` | The Makefile and the first engine code needed them. You asked for `compile_commands.json` so clangd works. |
| ch03 | Added the test runner's design: one program per test file, `RUN`/`CHECK`/`CHECK_EQ`, linking tests against `libmomo.a`, how `make test` runs them | Plan §4.10 only said "a tiny test runner". |
| ch03 | The debug build now stops at the first sanitizer report (`-fno-sanitize-recover=all`) | Writing the tests showed that a test with signed overflow passed while UBSan only printed a warning. |
| ch03 | Added `min`, `max` and `clamp` to `base.h` | The runner needed real code to test, and chapters 04, 09 and 23 need these functions. |
| ch04 | Added the arena details: the `Arena` struct and functions, zeroing in push, aligning addresses, the sizes, who resets which arena, the accessors | Plan §4.2 only described the three arenas. |
| ch04 | The boundary became `momo.h` plus the module headers it includes, and `MOMO_API` moved to `base.h` | `arena.h` is the first engine module the game calls into. |
| ch04 | Allowed `arena::push<T>` and `push_array<T>` as templates | They're typed wrappers over one untyped function, clearer than a macro. |
| after ch04 | Moved the outline (§8) to `outline.md` and this change log (§10) to `changelog.md`. §8 stays as a pointer, so older links still work. | The plan was growing every chapter. Both are lists rather than decisions, and the plan reads faster without them. |
| after ch04 | Shortened the rows added in ch01–ch04 to the decision and its reason, and added that rule to the plan's introduction | Struct fields, function names, paths and sizes were already in the code and the chapters. Repeating them added several long rows to the plan every chapter. |
| ch05 | `str_fmt` became `str::fmt`, and the plan gained the `Str` details: an `i32` length, and a 0 after formatted text | The namespace rule in §3.4, and writing the code. |
| ch05 | Added the log: `LOG_INFO`, `LOG_WARN` and `LOG_ERROR` macros around `logger::print`, writing to stderr. The outline's `log::info` changed with it. | Only a macro can pass on the caller's `__FILE__` and `__LINE__`. `log` is a C library function, so it can't be a namespace. Output on stdout was lost when the game crashed. |
| ch05 | `i64` and `u64` are now `long long` and `unsigned long long` | Chapter 03's `(long long)` casts would otherwise have spread to every log line. |
| ch06 | Added the reload details: checking the modification time every frame, closing before opening, waiting for the next build when a load fails, declaring `GameState` without defining it, and restarting for engine changes | Plan §4.1 only said that the engine reloads `game.so` when the file changes. |
| ch06 | The Makefile links `game.so` under a temporary name and renames it into place | Without the rename, the engine loaded a half-written `game.so` on every rebuild. |
| ch06 | Added a fourth arena, the engine's own. Permanent and stage became the game's alone. | Starting the game over after a layout change resets the permanent arena, which would have wiped the engine's data, and chapter 21 should snapshot only the game's memory. |
| ch06 | The loop runs until Ctrl+C, about 60 times a second. The outline says so. | Hot reload needs a game that keeps running. Chapters 07 and 09 replace the Ctrl+C handler and the sleep. |
| ch07 | Added the platform layer: SDL wherever it has the function, the OS only for reserving memory, nothing `MOMO_API`, and only the engine compiled and linked with SDL | Plan §4.4 only said "SDL3 behind `platform::`". |
| ch07 | Closing the window, Ctrl+C and `kill` all become SDL's quit event, replacing chapter 06's `SIGINT` handler | SDL installs the signal handlers itself, and the window adds a second way to quit. |
| ch07 | The debug build skips LeakSanitizer reports that pass through SDL | The graphics driver's memory looked leaked once `SDL_Quit` unloaded the driver, so every debug run failed when it quit. |
| ch07 | Chapter 07 fills the window with one color until chapter 08, and the outline says so | A Wayland compositor shows no window until it has a picture. |
| ch07 | Chapter 21 also decides whether losing focus pauses the game, and the outline says so | Plan §4.4 says it does, but a game that pauses can't keep looping while you edit its code in another window. |
| ch08 | Added the OpenGL details: `platform::` makes the context and `renderer::` makes every call, what the debug callback does with each message, a debug context in both builds, and vsync off until chapter 09 | Plan §4.5 only named OpenGL 4.6, glad, DSA and the debug callback. The callback first stopped at every error, until a shader with a typo showed that Mesa reports compile failures as errors too. |
| ch08 | Added how glad is generated and how vendored C code is built | glad is momo's first vendored library and its first C code. |
| ch08 | Chapter 09 also decides vsync, and the outline says so | Chapter 08 turned vsync off, so that the loop's sleep sets the pace on every video driver until chapter 09 replaces it. |
| ch09 | Added the fixed timestep: ticks and frames, integer nanoseconds handed to the timestep instead of read by it, and a cap of 6 ticks a frame with the dropped time logged | Plan §4.3 only said "fixed 60 Hz game updates" and "ticks per frame are capped". The cap's size came from measuring: on Wayland, 13 frames at the start of every run take 50 ms each. |
| ch09 | vsync is on, replacing chapter 08's "off until chapter 09" | With a fixed timestep, the frame rate no longer changes the game's speed, so the display can set it. |
| ch09 | The game counts its own ticks, and `momo::frame_index()` is gone | Frames depend on the display, and chapter 21's replays rewind only the game's memory. |
| after ch09 | Added `.clang-format`, `.editorconfig` and `make format`. The format is WebKit style with 13 changes, chosen to match the code as it was, and the reformat changed about 30 lines. | Neovim formats C++ with clang-format, whose default style gave a 2,208-line diff for the 1,894 lines of code. Matching the existing style instead brought that down to 64 lines. |
| after ch09 | Added `.clang-tidy` and `make lint`, and `make lint` joined the checks before each commit. Every finding fails it. It found a table of constants that wasn't `constexpr`, a test that stored a `char` in an `i64`, and a multiplication done in `i32` before it was widened. | Lint is useful only at zero findings: then any new finding stands out. The hand-picked checks enforce §3.4's names and §3.2's ban on globals. The usual `cppcoreguidelines` and `modernize` sets are left out because they fight the dialect, and so are two `bugprone` checks: one flags most of momo's function signatures, the other every bit operation on a signed size, such as `align & (align - 1)`. |
| ch10 | The game draws only in `render`, which gets a `const GameState*` and runs once per frame after the ticks. Drawing anywhere else is an `ASSERT`. | Plan §4.1 named `render` but not when it runs or what it may change. Chapter 09 made ticks and frames different rates. |
| ch10 | Added the batch: one instance per rectangle, one draw call per frame, a counting sort into layer order, a fixed capacity, and the sort in a module that never calls OpenGL | Plan §4.5 only said "batched sprites, drawn in as few calls as possible". Measured with 3,877 rectangles a frame: 1.6 ms drawn LearnOpenGL's way, 0.11 ms in one call. |
| ch10 | Layers are numbers, 0 to 7. The game names them with its own enum, and the engine gives them no meaning. | The first draft of chapter 10 had the engine name four layers. You pointed out that what a layer means is the game's decision, and the engine needs only how many there can be. |
| ch10 | Colors are RGBA bytes, with alpha blending on | The plan didn't say. Shadows, chapter 13's text and chapter 19's hitboxes need see-through rectangles. |
| ch10 | momo checks shader compile status itself, and turns off the shader compiler's debug messages | Chapter 08 found that Mesa also reports a failed compile through the debug callback. Writing the shaders confirmed it: each error was logged twice. |
| ch10 | The renderer takes whole pixels as `i32`, with no matrix, replacing §4.6's "float `V2` and matrices" | Every position the game draws is a whole pixel on a screen with no zoom or rotation, so the screen's size is all the vertex shader needs. |
| ch10 | The outline says chapter 10 also gives the game its `render` and compiles the first shaders | Both arrived with the first drawing. |
| ch11 | Added the virtual screen: a 256×240 texture the game draws on, copied into the window at the largest whole-number scale that fits, with black around it. The screen's size stays in the engine. | Plan §4.5 only said "scaled up by whole numbers, with black bars". |
| ch11 | The window asks for every pixel it covers, and the scale is chosen in pixels | A capture of chapter 10's window showed the compositor blurring every edge, even at scale 2. |
| ch11 | The window is resizable, and the renderer reads its size every frame instead of handling resize events | Plan §4.4 said the engine handles resizing, but not how. |
| ch11 | The outline says chapter 11 also made the window resizable and asked for every pixel | Both arrived with the virtual screen. |
| ch12 | Added textures: each rectangle shows a source cut from a texture, a rectangle of one color shows texture 0, a white pixel, and rows are never flipped. `draw_sprite` has no flags yet. | Plan §4.5 named `draw_sprite` but not how a rectangle picks its texture, or what becomes of plain rectangles. Nothing flips yet. |
| ch12 | The frame is drawn with one draw call per run of rectangles that share a texture | Measured with 3,880 rectangles: changing the texture before each draw call cost about 0.4 µs a change. Texture slots, Hazel's way, were measured too: correct and fast on Mesa, but undefined in GLSL. |
| ch12 | A texture is a number in the renderer's table, and each file is loaded once, for the whole run | `GameState` holds numbers, and the game loads its textures again whenever it starts over. Chapter 33 needs each texture's path to reload it. |
| ch12 | The 8×8 font is engine code, made into a texture when the renderer starts, and `draw_text` draws with it | Chapter 13's overlay needs text that works without any file, and the game needed READY. |
| ch12 | Added `platform::read_file`. A file's bytes and pixels come from `malloc` and are given back before `load_texture` returns. | stb_image decodes bytes it's handed, and the platform reads files. No arena fits memory that lives for one function call. |
| ch12 | Pictures are PNG files in `assets/`, copied next to the executable, until chapter 30's bake tool. stb_image 2.30 is vendored, PNG only. | Plan §6 has runtime code load momo's own formats, from a tool that doesn't exist yet. |
| ch12 | The outline says chapter 12 also gave the game `draw_text` and its first picture | Both came with the font and the first texture. |
